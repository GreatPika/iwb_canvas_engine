# Research: P11 Draw Tools Current Facts

## Summary

P11 is already framed as the phase that turns existing public draw-related DTOs, preview variants, pointer routing, cleanup policy, edit commits, geometry, and overlay rendering into pencil, marker, and line tool behavior. The repository currently defines many of those boundaries before the draw machines themselves exist: public API exposes `CanvasDrawTool`, `CanvasDrawStyle`, pointer samples/policies, stroke and line document elements, draw preview variants, and typed draw action payloads, while runtime/interaction code currently implements tool settings, move/marquee pointer handling, preview publication, cleanup coordination, and edit commit delivery.

The current implementation does not contain draw, stroke, or line lifecycle machines. In draw mode, pointer input is currently a P10 compatibility no-op except cleanup-capable terminal handling; tests and docs explicitly preserve that state until P11. Existing contracts require P11 to consume the P10 cleanup coordinator, commit through `EditKernel`, publish preview-only changes through `state.revisions.preview`, publish interaction setting changes through `state.revisions.interaction`, use overlay-only repaint for draw previews, and preserve pending line state on `interactive=false` when the pending line is not owned by an active routed pointer session.

The public incremental smoke flow matters because it is the external consumer compatibility path: it imports only the package root barrel, decodes schema v1 data, constructs and drives `CanvasRuntime`, mounts `CanvasSurface`, mutates through public ports, and asserts public state/action behavior. P11 design inputs must account for this flow because draw tools will extend the same public `CanvasRuntime.tools`, `runtime.preview`, `runtime.state`, `runtime.actions`, `CanvasSurface`, edit, load, and command surfaces already covered there.
