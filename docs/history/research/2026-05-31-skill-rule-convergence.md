# Research: Skill Rule Convergence

## Executive Summary

The repository-local skills already behave like one staged governance system: research and forensics gather facts, design locks architecture form, contract authoring turns locked decisions into executable units, contract checking prevents unresolved decisions from reaching implementation, unit-by-unit implementation proves and reviews each unit, and review skills police proof, ownership, naming, source-of-truth, and completion claims. The same invariants recur across these stages, often with different names: direct proof versus proxy proof, decision traceability, source-input preservation, source-of-truth ownership, owner-level fixes, boundary-owned validation, sequencing, temporal/reentrancy windows, all-or-nothing behavior, negative proof, fresh reviewers, and completion evidence.

Some shared vocabulary already exists. `Outcome-Proof Fit` is explicitly declared as shared in `anti-slop-review` and reused by design, contract, and contract-check skills (`.agents/skills/anti-slop-review/SKILL.md:26`, `.agents/skills/architecture-design/SKILL.md:131`, `.agents/skills/change-contract/SKILL.md:367`, `.agents/skills/change-contract-check/SKILL.md:146`). `Decision Trace` is also structurally shared from design to contract (`.agents/skills/architecture-design/SKILL.md:174`, `.agents/skills/change-contract/SKILL.md:143`). Other equally important invariants are not named consistently: fresh/clean reviewer rules, owner-level root-cause fixes, fixture quarantine, decision closure, and stage boundary rules are repeated as local prose.

The highest-value normalization is not generic cleanup. It is to give repeated behavior-affecting invariants stable names, then keep stage-specific detail close to the skill that applies it. The main risk if unchanged is not cosmetic inconsistency; it is agent behavior drift: a future agent may treat a proxy as proof in one stage, drop a design handoff when drafting a contract, patch a symptom locally after repeated review findings, reuse a stale reviewer after repair, or mark a plan/unit complete before proof exists.

## Detailed Findings

### 1. Stage Boundary

- **Canonical concept**: `Stage Boundary`.
- **Current instances**: design authoring does not implement, draft a Change Contract, or edit outside `.design/` (`.agents/skills/architecture-design/SKILL.md:10`, `.agents/skills/architecture-design/SKILL.md:11`); design workflow validates only and does not implement, draft a Change Contract, or edit outside `.design/` (`.agents/skills/architecture-design-workflow/SKILL.md:11`, `.agents/skills/architecture-design-workflow/SKILL.md:12`); change-contract does not edit code, implement, or run the work (`.agents/skills/change-contract/SKILL.md:10`); change-contract-check validates contract, not code (`.agents/skills/change-contract-check/SKILL.md:8`); plan-step coordinates authoring/validation only and does not implement code unless separately asked after acceptance (`.agents/skills/plan-step-contract/SKILL.md:11`, `.agents/skills/plan-step-contract/SKILL.md:13`); unit-by-unit implements one unchecked unit at a time (`.agents/skills/unit-by-unit/SKILL.md:13`, `.agents/skills/unit-by-unit/SKILL.md:14`); research documents the codebase as it exists and forbids suggestions/critique/proposed changes (`.agents/skills/research-codebase/SKILL.md:12`, `.agents/skills/research-codebase/SKILL.md:16`, `.agents/skills/research-codebase/SKILL.md:19`); repo-forensics is used when mechanical evidence is needed before a fix, refactor, review, or architecture decision (`.agents/skills/repo-forensics/SKILL.md:8`, `.agents/skills/repo-forensics/SKILL.md:9`).
- **Current wording summary**: Each skill defines what stage it owns and what it must not do. The rule is repeated as edit-scope restrictions, output restrictions, or "before" wording rather than one shared concept.
- **Stage semantics**: Applies to all stages. Design and plan authoring may edit limited artifacts; research writes `.research`; review/check skills are audit-only unless a separate repair path exists; implementation changes code only one accepted unit at a time.
- **Divergence**: The same boundary rule is named by local activity: "do not implement", "validate the contract, not the code", "document and explain", "mechanical evidence before a fix". The shared "stage boundary" concept is not named.
- **Recommendation**: Introduce the shared name `Stage Boundary` in cross-stage skills, with each skill retaining its local allowed outputs and edit scope.
- **Risk if unchanged**: Agents can blend stages, such as making implementation changes during design, authoring a contract from a blocked design, or using research/forensics as permission to change code.

### 2. Decision Closure

- **Canonical concept**: `Decision Closure`.
- **Current instances**: change-contract says a full contract must settle decisions before implementation and output `Contract Blocker` if the implementer would still choose owner, boundary, source of truth, compatibility, execution order, proof seam, temporal behavior, all-or-nothing behavior, migration, or completion signal (`.agents/skills/change-contract/SKILL.md:34`, `.agents/skills/change-contract/SKILL.md:38`, `.agents/skills/change-contract/SKILL.md:41`, `.agents/skills/change-contract/SKILL.md:56`); change-contract-check says a full contract is not implementable when the implementer must choose those decisions (`.agents/skills/change-contract-check/SKILL.md:22`, `.agents/skills/change-contract-check/SKILL.md:24`, `.agents/skills/change-contract-check/SKILL.md:27`); design review defines `PASS` as no new architecture decision needed and `BLOCKED` as "do not write a Change Contract yet" (`.agents/skills/architecture-design-review/SKILL.md:43`, `.agents/skills/architecture-design-review/SKILL.md:50`); design dispositions include `READY_FOR_CONTRACT`, `ARCHITECTURE_GATE`, `NEEDS_RESEARCH`, and `DESIGN_NOT_REQUIRED` (`.agents/skills/architecture-design/SKILL.md:44`, `.agents/skills/architecture-design/SKILL.md:48`, `.agents/skills/architecture-design/SKILL.md:53`); design workflow classifies `BLOCKED` routes before editing and records terminal blockers in `.design` (`.agents/skills/architecture-design-workflow/SKILL.md:42`, `.agents/skills/architecture-design-workflow/SKILL.md:43`, `.agents/skills/architecture-design-workflow/SKILL.md:49`).
- **Current wording summary**: Unresolved owner, boundary, source-of-truth, compatibility, proof, sequencing, product, or factual decisions must not be deferred into implementation.
- **Stage semantics**: Design uses dispositions; design review uses verdicts and routes; contract authoring emits `Contract Blocker`; contract checking blocks implementation.
- **Divergence**: The same rule has different stage labels (`ARCHITECTURE_GATE`, `NEEDS_RESEARCH`, `BLOCKED`, `Contract Blocker`) and not all stages name the invariant behind the label.
- **Recommendation**: Introduce `Decision Closure` as the invariant, then keep the existing stage-specific verdict/disposition vocabulary as its application.
- **Risk if unchanged**: Agents may treat unresolved architecture or proof questions as local implementation tactics.

- **Current wording summary**: Evidence must be concrete, checked, and tied to the consequence it supports; tool output and citations are not decisions by themselves.
- **Stage semantics**: Research and forensics collect evidence; design/contract authoring cite it; reviewers re-check it.

- **Risk if unchanged**: Agents may cite broad files, stale citations, or tool output without explaining why it constrains the next decision.

## Recommended Normalization Order

1. **Outcome-Proof Fit**: Already named and widely used; finish normalization by making code-review references use the canonical name.
2. **Decision Chain Of Custody**: High cross-stage risk; unify source inputs, Decision Trace, handoff constraints, and source-input obligations.
3. **Decision Closure**: Clarify how design dispositions, review verdicts, `Contract Blocker`, and `BLOCKED` all express one unresolved-decision rule.
4. **Completion Evidence Boundary**: Prevent plan/unit/design completion markers from being interpreted at the wrong stage.
5. **Source-Of-Truth Singularity**: Normalize the single-owner rule and explicitly include the cache/performance duplication exception plus consumer requirement.
6. **Negative Proof And Fixture Quarantine**: Unify negative proof, bypass proof, structural proof, and fixture-only contamination rules.
7. **Temporal Surface Closure** and **All-Or-Nothing Failure Boundary**: Normalize names and field lists because these rules are precise and easy to weaken accidentally.
8. **Owner-Level Fix** and **Boundary-Owned Policy**: Normalize shared owner/boundary vocabulary after the proof and traceability rules are stable.
9. **Fresh Reviewer After Mutation** and **Prompt Context Minimalism**: Normalize wording only after deciding whether these are general workflow rules or intentionally local to current orchestrator skills.
10. **UI Metadata Separation**: Handle as a metadata polish/safety pass after behavior-rule vocabulary is decided.
