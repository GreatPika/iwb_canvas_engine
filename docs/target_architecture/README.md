# Target Architecture Map

## Purpose

This directory is the verification-first target map for
[`ADR 0001`](../adr/0001_target_engine_architecture.md).

It keeps the target form short and code-backed:

- ADR 0001 fixes the accepted top-level target.
- `docs/target_architecture/**` refines that target into a working map.
- `ARCHITECTURE.md` remains the checked-in current-state architecture contract.
- `PLAN.md` and `plan/*.md` remain execution-order artifacts, not target-map
  levels.

## Directory Roles

- [`overview.md`](overview.md) is Level 1: the owner-family registry plus the
  shared verification-status vocabulary.
- [`families/*.md`](families) are Level 2: one compact family contract per
  owner family using `Purpose`, `Target Rules`, `Owners`, `Forbidden Shapes`,
  `Mechanical Evidence`, and `Status`.
- [`execution_flows.md`](execution_flows.md) is the runtime-view layer: a short
  registry of mechanically supported runtime-center flows and the boundaries
  they verify.
- [`evidence/`](evidence) is the evidence layer: committed machine-generated
  `.json` and `.md` artifacts referenced by the target map.
- [`PLAN.md`](/Users/blackpika/iwb_canvas_engine/PLAN.md) and
  [`plan/*.md`](/Users/blackpika/iwb_canvas_engine/plan) record migration order
  and slice contracts only.

## Mechanical Evidence

All target-map flow, path, and diagram references must come from committed
artifacts generated by checked-in repository probes.

Use only repository-local commands:

- `dart run tool/lsp_find_symbols.dart <query>`
- `dart run tool/lsp_trace_symbol.dart <file> <symbol> --depth=N`
- `dart run tool/lsp_trace_flow.dart <file> <symbol> --depth=N`
- `dart run tool/lsp_find_boundary_bypasses.dart <file> <class> --must-pass=<seam>`
- `dart run tool/lsp_find_thin_wrappers.dart <file-or-dir>`
- `dart run tool/run_tool_tests.dart test/tool/target_architecture_map_tool_test.dart`

Target-map documents do not carry hand-written Mermaid diagrams or hand-written
flow/path inventories. They point to committed evidence under
[`evidence/`](evidence) instead.

## Verification Workflow

1. Confirm the accepted top-level rule in
   [`ADR 0001`](../adr/0001_target_engine_architecture.md).
2. Use [`overview.md`](overview.md) to choose the owner family and current
   verification status.
3. Use [`execution_flows.md`](execution_flows.md) and the relevant family doc
   to identify the required boundary and evidence entrypoint.
4. Run the repository-local probe command named by the target map and update
   the committed evidence artifact when the checked-in code changes.
5. Decide whether the drift is in the code or in the target map before opening
   a new plan step.

## Update Rules

- Keep this directory short and normative; long mismatch narrative belongs in
  execution contracts, not in the target map.
- Keep target-state rules here and checked-in current-state rules in
  [`ARCHITECTURE.md`](/Users/blackpika/iwb_canvas_engine/ARCHITECTURE.md).
- Add a new owner family only after an accepted top-level owner decision exists.
- Keep the shared verification-status vocabulary in [`overview.md`](overview.md)
  aligned with every family doc.
