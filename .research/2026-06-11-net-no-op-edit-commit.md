# Research: Net No-Op Edit Commit

## Summary

The stage report identifies EDIT-002 as a P2/R2 issue: an edit callback can mutate document facts and then restore them inside the same commit, while the current commit delta remains based on intermediate operations rather than a final comparison with the original committed facts (`iwb_canvas_engine_12_stage_reports.md:1`, `iwb_canvas_engine_12_stage_reports.md:7`). The report names background color rollback, temporary add/remove, and palette rollback as scenarios where the final document can match the starting document while revisions, effects, listeners, and cache invalidation still run (`iwb_canvas_engine_12_stage_reports.md:35`, `iwb_canvas_engine_12_stage_reports.md:48`).

The current edit path is operation-journal based. `DraftDocument` stores a mutable `StoreRevisionDelta` and derives `didChange` from whether that accumulated delta has any flags (`lib/src/edit/draft_document.dart:61`, `lib/src/edit/draft_document.dart:64`). It also accumulates touched facts through `TouchedSetBuilder`, whose touch methods mutate sets/flags directly and whose `build()` method emits the accumulated `TouchedSet` (`lib/src/edit/touched_set_builder.dart:7`, `lib/src/edit/touched_set_builder.dart:25`, `lib/src/edit/touched_set_builder.dart:97`). Sparse edit sessions similarly record sparse mutations, touched state, and an accumulated `StoreRevisionDelta` during the callback (`lib/src/edit/edit_session.dart:326`, `lib/src/edit/edit_session.dart:327`, `lib/src/edit/edit_session.dart:329`). `DocumentStoreKernel.prepareSparseCommit` applies sparse mutations sequentially and treats the commit as changed if any applied mutation changed the running `nextDocument` (`lib/src/store/document_store_kernel.dart:343`, `lib/src/store/document_store_kernel.dart:344`, `lib/src/store/document_store_kernel.dart:361`, `lib/src/store/document_store_kernel.dart:373`).

The public delivery path uses the resulting revision delta to decide whether to install the document, publish state, and deliver effects. `EditKernel.edit` installs only when `plan.hasChanges` is true (`lib/src/edit/edit_kernel.dart:83`, `lib/src/edit/edit_kernel.dart:84`), `CommitPlan.hasChanges` is true when `revisionDelta.hasChanges` or a selection effect exists (`lib/src/edit/commit_plan.dart:56`), and `CommitApplier` publishes state when the plan advances the document revision or selection changes (`lib/src/edit/commit_applier.dart:99`, `lib/src/edit/commit_applier.dart:100`, `lib/src/edit/commit_applier.dart:101`). Runtime delivery directly applies spatial and resource effects, publishes public state when requested, and sends non-empty effect lists to the commit-effect observer (`lib/src/runtime/runtime_root.dart:1638`, `lib/src/runtime/runtime_root.dart:1639`, `lib/src/runtime/runtime_root.dart:1640`, `lib/src/runtime/runtime_root.dart:1647`). The contract states that a no-op edit does not publish a new snapshot (`docs/contracts/edit_kernel.md:260`, `docs/contracts/edit_kernel.md:262`, `docs/contracts/edit_kernel.md:263`).

## Observed Architecture Facts

- Pattern observed: `EditKernel` is the synchronous edit session and commit/rollback coordinator (`docs/architecture/01_runtime_ownership.md:60`), and runtime wires it to `DocumentStoreKernel.prepareSparseCommit`, `_applyEditCommit`, and `_deliverEditCommitResult` (`lib/src/runtime/runtime_root.dart:216`, `lib/src/runtime/runtime_root.dart:221`, `lib/src/runtime/runtime_root.dart:222`, `lib/src/runtime/runtime_root.dart:223`).
- Pattern observed: materialized and sparse routes both compile commit plans from `StoreRevisionDelta` and `TouchedSet`. The contract states both routes use `CommitCompiler` and must produce the same operation-matrix effects for the same accepted public edit (`docs/contracts/edit_kernel.md:198`, `docs/contracts/edit_kernel.md:201`, `docs/contracts/edit_kernel.md:202`).
