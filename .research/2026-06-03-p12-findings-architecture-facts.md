# Research: P12 Findings Architecture Facts

## Summary

P12 context-action requests are produced from a runtime-owned read path that resolves spatial context candidates, maps the result into `ContextTargetReadFacts`, issues guard facts in `InteractionRequestRegistry`, and emits a public `CanvasContextActionRequested` through a separate runtime stream. Spatial query trust is represented as typed query facts: `SpatialCandidatesResult` becomes `InteractionReadQueryStatus.candidates`, while invalid, stale, and budget-exceeded spatial results become non-candidate statuses. In the current context-target adapter, the public target kind is still selected from `hitFacts == null`, so a non-candidate spatial result with no resolved hit returns `ContextTargetReadFacts.emptyCanvas`.

Context-action request delivery and committed action delivery use different stream controller declarations. `CanvasActionCommitted` uses a synchronous broadcast controller, while context-action requests use a default broadcast controller. Tests that observe context requests call a zero-duration async flush before asserting received requests. The registry stores every issued request id in a map and retirement rewrites the stored value with `retired: true`; no clear, remove, purge, or dispose method is declared on the registry.

The P12 read-fact models currently defensively copy the new eraser iterable fields, and behavior tests assert those fields are unmodifiable. The structural guardrail for `interaction.read_port_immutable_facts` still enumerates only older selected-move and marquee fields. The text-edit stale commit guardrail is registered and runner-backed, but its scanner checks marker order in the `commitTextEdit` method body. Documentation contains both historical P10 text saying double tap/context requests are unsupported or empty, and P12 text saying context-action request production is implemented.
