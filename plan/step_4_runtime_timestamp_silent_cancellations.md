# Change Contract

## Goal

Runtime outputs that are suppressed or cancelled before public delivery must not
consume the runtime timestamp cursor, while accepted context-action requests,
accepted selected-move resolver requests, and accepted actions keep the
documented runtime-local monotonic timestamp behavior.

## Boundaries

Owner: `RuntimeActionFinalizer` owns timestamp cursor state and candidate/commit semantics. `RuntimeRoot` owns runtime output delivery boundaries: pending context request delivery/suppression and selected-move resolver request acceptance/cancel. `InteractionEngine` may pass timestamp hints or request builders but must not own the cursor.

In Scope:

- Update normative interaction contract text and context-action request diagrams so they describe delivery-time timestamp resolution for queued context requests and timestamp-silent suppression before delivery.
- Add a finalizer-owned way to compute a timestamp candidate without advancing the cursor until the owning runtime boundary commits it.
- Defer context-action request timestamp resolution until the queued request is actually delivered to `contextActionRequests`.
- Ensure load/dispose cleanup of queued context requests discards unresolved timestamp work and does not advance the cursor.
- Use synchronous tentative timestamp handling for selected-move resolver requests so `CanvasMoveCommitRequest.timestampMs` is available during the resolver callback, but resolver cancel and resolver-returned zero delta do not consume the cursor.
- Preserve accepted selected-move resolver request/action ordering: the resolver request timestamp is committed before the accepted move action is finalized, so the action timestamp remains later and distinct.
- Update public timestamp source-of-truth docs for selected-move resolver callbacks so tentative callback candidates are not confused with committed accepted resolver request timestamps.
- Add focused regression tests for cursor continuity after suppressed queued context requests and selected-move resolver cancel.

Out of Scope:

- Changing public DTO shapes, public stream names, `CanvasMoveCommitRequest` fields, `CanvasContextActionRequested` fields, or timestamp value type.
- Changing timestamp semantics for accepted actions, accepted context-action request delivery, pending line previews, document revisions, selection revisions, or schema data.
- Reworking interaction target admission, spatial reads, context request guard facts, selected-move commit math, move resolver public API, or edit/store commit behavior.
- Changing resolver exception semantics beyond preserving existing preview cleanup and rethrow behavior.
- Adding durable timestamp state to documents, schemas, resources, selection state, preview revisions, or any source outside the runtime-local finalizer.
- Reordering public context request delivery relative to the existing scheduled microtask beyond resolving timestamp at delivery time.

Source of Truth: `docs/contracts/public_api_v1.md` and `docs/contracts/operation_matrix.md` own public timestamp semantics, including the distinction between tentative selected-move resolver callback candidates and committed accepted resolver request timestamps. `docs/verification/guardrails.md` and `docs/verification/guardrail_design_patterns.md` own repository verification guardrail wording for runtime-created timestamp invariants and no-output proof patterns. `RuntimeActionFinalizer` implements the single runtime-local cursor. `RuntimeRoot` owns the commit/discard boundary for runtime outputs that may be suppressed or cancelled. No new durable source of truth for timestamp state may be introduced.

`docs/contracts/interaction_engine.md`, `docs/diagrams/seq_context_action_request.mmd`, and `docs/diagrams/state_pending_context_action_request.mmd` own interaction-flow order and must be updated with the same delivery-time timestamp boundary as the implementation.

Compatibility: Accepted action timestamp monotonicity, accepted context-action request delivery, accepted selected-move resolver request/action timestamp ordering, resolver callback synchrony, request guard cleanup, and load/dispose suppression behavior must remain source-compatible. Existing public signatures and DTO field shapes must remain unchanged.

Order Constraints:

1. Establish finalizer-owned candidate/commit/discard semantics before migrating runtime call sites.
2. Migrate context-action request timestamp timing and update the matching interaction contract/diagrams in the same execution unit, so no committed unit leaves normative source-of-truth drift.
3. Migrate selected-move resolver timestamp timing and update the public timestamp contract, operation matrix, and verification guardrail docs in the same execution unit, after the finalizer candidate boundary exists and before extending resolver cancel tests.
4. Preserve accepted-path timestamp tests while adding suppressed/cancelled continuity tests.
5. After Unit 3, run the final focused runtime/interaction tests, docs checks, architecture diagram generation checks, and repository verification for all changed owners as part of Unit 3 completion.

Temporal Surface Closure:

- Context request admission may run synchronously from `RuntimeRoot.handleDoubleTap` and pointer handling, but `CanvasContextActionRequested.timestampMs` must be resolved only inside the scheduled delivery boundary after closed-stream and generation discard filtering have selected an already-deliverable pending payload, immediately before adding the request to `_contextActionRequests`. If load or dispose cleanup runs before that microtask, `_suppressPendingContextRequests` and closed-stream/generation filtering are discard boundaries and no timestamp cursor change is allowed.
- Selected-move resolver callback is synchronous. The resolver request timestamp must be a finalizer-owned candidate available to `CanvasMoveCommitRequest` during `runResolverCallback`. The candidate commits after the resolver returns a finite non-zero delta and before selected-move edit preparation/action finalization begins. It discards on `CanvasMoveCancel` or zero resolved delta. Resolver exceptions preserve existing compatibility by committing the candidate before cleanup/rethrow, because the callback already observed `CanvasMoveCommitRequest.timestampMs` under current eager-reservation behavior. Reentrant public runtime mutation from inside the resolver remains rejected by the existing runtime mutation guard.
- Accepted actions still commit timestamps at action finalization. The selected-move accepted resolver request candidate must be committed before the move action timestamp is finalized, preserving request timestamp then action timestamp publication order.

All-Or-Nothing Failure Boundary:

- Context request delivery irreversible point: adding `CanvasContextActionRequested` to `_contextActionRequests`. Fallible or suppressible work before that point includes target admission, request fact registration, queued microtask delay, load cleanup, dispose cleanup, closed-stream handling, and generation filtering. Timestamp commit for context requests must occur only for pending payloads that have already passed closed-stream and generation filtering, immediately before building and adding the public request. If load/dispose suppression, stream close, or generation mismatch happens first, the failure projection is no public request and no finalizer cursor advancement. Direct proof must fail if request admission, pending storage, suppression, closed-stream handling, or generation-filter discard paths resolve or commit the timestamp.
- Selected-move resolver irreversible points: for accepted resolver output, finalizer commit of the resolver request candidate occurs after the resolver returns a finite non-zero delta and before selected-move edit preparation begins; for thrown resolver callbacks, finalizer commit occurs in the resolver-error path before cleanup/rethrow to preserve current cursor-consumption compatibility after the callback observed `CanvasMoveCommitRequest.timestampMs`. Fallible work before the accepted-output point includes resolver callback execution and finite/non-zero delta validation. Later edit preparation and delivery work may fail or throw, but the resolver request has already been synchronously observed by the app callback as a timestamped runtime output, so the candidate commit is no longer reversible. If resolver cancel or zero delta happens before the accepted-output irreversible point, the failure projection is cleanup/no accepted move action and no cursor advancement from the resolver request candidate. Direct proof must fail if the candidate commits before cancel/zero is known or fails to commit for a thrown callback.
